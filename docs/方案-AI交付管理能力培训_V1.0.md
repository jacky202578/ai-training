## Part 1：能审 — 看懂AI的输出

### 第1课：像看图纸一样看代码

> **核心理念**：代码就是另一种图纸。设计师看图纸不看线条的粗细，看的是结构和意图。你看代码也一样。

**学习目标**
- 理解代码是什么、为什么需要结构
- 能辨认HTML/CSS/JS三类代码，知道各自负责什么
- 能用「画面对应法」找出一段代码管的是页面上的哪一块

**核心概念（用工厂类比讲解）**

| 概念 | 工厂类比 | 在你的项目里 |
|------|---------|------------|
| HTML | 车间平面图 | 气泡图的画布框架、8D工作台的表单结构 |
| CSS | 装修规范 | 气泡颜色大小、8D表单的按钮/卡片样式 |
| JavaScript | 设备控制程序 | 点击按钮发生什么、数据从哪取来 |

**动手练习（用气泡图项目）**
1. 打开 `bubble-chart-demo.html`，对照浏览器中渲染的4个案例卡片，用 Ctrl+F 搜索关键词（如「供应商」「孔径」），定位对应的HTML代码块
2. 用浏览器 F12「审查元素」，点击页面上的一个气泡（如供应商A的绿色圆圈），观察对应的 `<circle>` 标签代码
3. 给你一段 8D工作台前端的分步向导代码（从 T10 中截取），用白话描述它渲染的界面长什么样

**考核标准**
- 能准确指出一段HTML代码对应页面上的哪个元素
- 能用F12在页面和源码之间建立对应关系
- 能分辨一段代码是HTML、CSS还是JavaScript

📝 **课前自测**：5道选择题（测你现在对HTML/CSS/JS的认知）
📋 **课后对比**：给你一段8D工作台前端代码，你先描述它渲染的界面长什么样 → AI独立描述 → 对比差异，看你和AI谁看得更准

### 第2课：看懂CSS改动的影响

> **核心理念**：你不需要会写CSS，但你需要在AI说「改了样式」的时候，能判断改对了吗？改坏了其他东西吗？

**学习目标**
- 理解CSS怎么控制排版和外观（位置、大小、颜色、间距）
- 能看懂AI的CSS改动影响什么视觉效果
- 能对比改前改后的页面，判断CSS改动是否正确

**核心概念（工厂类比）**

| CSS概念 | 工厂类比 | 在气泡图中的例子 |
|---------|---------|----------------|
| `width` / `height` | 工件长宽 | 气泡图卡片的宽度 |
| `margin` | 零件到边缘的距离 | 卡片之间的间距 |
| `padding` | 孔内壁的预留余量 | 卡片内部文字到边框的距离 |
| `color` / `background` | 表面处理和涂装 | 气泡颜色、卡片背景色 |
| `border-radius` | 倒角半径 | 卡片圆角 |
| `font-size` | 刻字规格 | 标题和正文的字号 |

**动手练习（用气泡图项目）**
1. 打开 `bubble-chart-demo.html`，用F12实时修改一个CSS属性（如把 `--accent: #3b82f6` 改成红色），看整个页面哪些地方变了
2. AI改了一段气泡图的CSS：把案例卡片从「2列网格」改成「3列」。给你这个改动（Git diff），判断改了什么，画出改动后的布局草图
3. 对比两张改动前后的截图，找出3个以上视觉差异，回到代码中定位对应的CSS规则

**考核标准**
- 拿到一个CSS diff，能用中文描述「把xx从A改成了B」
- 能从代码改动推断出对布局/颜色/字体的具体影响
- 对比截图能定位代码中的对应CSS属性

📝 **课前自测**：5道选择题（CSS基础概念：margin/padding/color/border-radius）
📋 **课后对比**：AI改了一段气泡图CSS，你先审查改了什么 → AI独立审查 → 对比你们的审查意见差异

### 第3课：看懂JavaScript逻辑 — if/else和数据流转

> **核心理念**：JavaScript就是一套「如果…就…否则…」的判断规则。你看合同条款怎么审的，看代码逻辑就怎么审。

**学习目标**
- 理解变量、条件判断（if/else）、循环（for）、函数四种基础结构
- 能追踪一段代码的「数据从哪来→经过什么判断→到哪去」
- 能识别条件判断中是否有遗漏的分支

**核心概念（8D工作台类比）**

| JS概念 | 8D工作台类比 | 代码示例 |
|--------|------------|---------|
| 变量 | 8D报告上的一个字段（如：8D编号） | `let reportId = "S-012";` |
| if/else | 门禁逻辑：D3→D4需要品质主管角色 | `if (user.role === "quality_manager") { 放行 } else { 拒绝 }` |
| for循环 | 遍历所有待审批的8D，逐个检查 | `for (const r of pendingReports) { 检查(r); }` |
| 函数 | D8关闭操作：输入8D报告→校验→返回结果 | `function close8D(report) { ... }` |

**动手练习**
1. 拿到8D工作台 T05 中的 D3 门禁逻辑代码（约15行），用中文写出它的判断流程：「首先检查…如果…就放行；否则检查…如果不满足…就拒绝」
2. 给你一段有bug的验证逻辑（例如：D3门禁只检查了 `role === "quality_manager"`，没检查「品质主管不能审自己当组长的8D」），找出遗漏的判断分支
3. 追踪气泡图中一个气泡的数据流：`circle` 标签里的 `cx`、`cy`、`r`、`fill` 这些值是怎么决定气泡显示在哪、多大、什么颜色的

**考核标准**
- 能读一段不超过20行的JS代码，用中文描述它的执行逻辑
- 能指出条件判断中缺少的边界情况
- 理解X/Y坐标→气泡位置、r值→气泡大小的映射关系

📝 **课前自测**：5道选择题（if/else逻辑、变量、循环的基本概念）
📋 **课后对比**：给你一段D3门禁的bug代码，你先找出漏洞 → AI独立审查 → 对比差异表

### 第4课：代码审查实战 — 完整审查一个AI交付的功能

> **核心理念**：前面三课是认识零件，这一课是看整台设备。用审查清单把HTML+CSS+JS串起来，做一次完整审查。

**学习目标**
- 建立代码审查的6项清单式检查流程
- 能从功能描述出发，逐项验证代码是否覆盖所有需求
- 能输出一份结构化的审查记录

**审查清单（Checklist）**

```
□ 1. 功能完整性：需求列的每个点，代码里都有对应的实现吗？
□ 2. 边界处理：空白输入、极端数值、特殊字符怎么处理？
□ 3. 数据安全：用户输入的数据有没有被校验？会不会丢？
□ 4. 用户体验：操作反馈（加载中、成功提示、失败提示）都有吗？
□ 5. 逻辑一致性：相似场景处理方式一致吗？
□ 6. 变更影响：改了这段代码，可能影响哪些其他功能？
```

**动手练习（用8D工作台前端代码）**
1. 从8D工作台 T09（泳道看板）或 T10（分步向导）中取一段已实现的功能代码
2. 用6项清单逐项审查，记录每项的结论
3. 提交你的审查记录 → AI独立审查同一段代码 → 系统生成差异对比表
4. 你漏了什么？误报了什么？谁的更有道理？带着差异进入总结反馈环节

```
【审查记录】
功能：8D分步向导D3步骤 — 根因分析表单
审查人：Jacky
日期：YYYY-MM-DD

[通过] 必填项校验 — 5Why和鱼骨图的字段都有required标记
[问题] 第XX行 — 鱼骨维度选择后没有校验最少3个维度的限制
        建议：在提交按钮的click事件中增加countFishboneDimensions()>=3的判断
[建议] 第YY行 — 5Why文本框建议增加placeholder提示"请至少填写3层原因分析"
```

**考核标准**
- 能独立完成一个功能模块的6项清单审查
- 审查记录包含：具体行号/位置、问题描述、修改建议
- 能在15分钟内完成对一个中型功能的审查

📝 **课前自测**：5道选择题（代码审查清单中的概念判断）
📋 **课后对比**：你的审查记录 vs AI的审查记录 → 差异对比表 → 分析漏报/误报

## Part 2：能验 — 验证逻辑正确性

### 第5课：数据从哪来到哪去 — 数据库与API

> **核心理念**：系统本质上是数据的搬运工。你管仓库知道「入库→存储→出库」的流转，理解数据流也是一样的道理。

**学习目标**
- 理解数据库是什么（类比Excel的多个关联Sheet）
- 理解前端→API→数据库的数据流向
- 能看懂AI的数据改动会不会导致数据丢失或不一致

**核心概念（8D工作台类比）**

| 概念 | 工厂类比 | 8D工作台实例 |
|------|---------|------------|
| 数据库表 | Excel的一个Sheet | `eight_d` 表 = 所有8D报告的Sheet |
| 字段（列） | Sheet的列名 | 表里有：编号、客户名、零件号、状态、组长… |
| 记录（行） | 一条数据 | 一行 = 一份8D报告 |
| API | 仓库管理员 | 前端说「给我S-012的报告」→ API去数据库取→返回 |
| JSON | 送货单格式 | API返回的 `{ "id": 12, "status": "D3", ... }` |

**动手练习**
1. 看8D工作台 T01 中的数据库设计（6张表），画出每张表里有什么字段（如 `eight_d` 表有：id、complaint_id、status、team_leader…）
2. 追踪一个操作的数据流：「操作工点击完成任务的拍照按钮」→ 图片上传到哪 → 任务的status怎么变 → 存在哪张表的哪个字段
3. AI给你的8D工作台加了一个新功能：任务增加「截止时间提醒」。检查：新增的 `reminder_sent` 字段有没有同步加到数据库建表语句（init_db.sql）中？

**考核标准**
- 能看懂数据库表结构中的字段清单
- 能追踪一个功能从用户操作到数据落库的完整链路
- 能发现「代码里用了新字段但数据库没建这个字段」的不一致

📝 **课前自测**：5道选择题（数据库表/字段/记录/API/JSON概念）
📋 **课后对比**：AI给8D工作台加了新功能，你和AI各自审查数据流 → 对比你们发现的字段不一致**

### 第6课：功能测试 — 不只是测「正常情况」

> **核心理念**：质检员不只测「标准件」，更要测各种异常情况。功能测试就是你的产品质检。

**学习目标**
- 理解正向测试和边界测试的区别
- 掌握测试用例编写方法
- 能对AI交付的功能独立执行验收测试

**测试用例模板**

```
用例编号 | 测试场景 | 操作步骤 | 测试数据 | 预期结果 | 实际结果 | 状态
TC-01   | 正常创建8D | 录入完整信息→提交 | 客诉S-001,8D编号S-012 | 8D创建成功，跳转详情 |  | ⬜
TC-02   | 空必填字段 | 不填客诉编号→提交 | 客诉编号留空 | toast提示「请选择关联客诉」 |  |
TC-03   | 超长文本   | 问题描述输入5000字 | 5000字文本 | 正常保存或提示字数限制 |  |
TC-04   | 特殊字符   | 零件号输入<script> | <script>alert(1) | 正常保存，不执行脚本 |  |
TC-05   | 重复提交   | 双击提交按钮 | — | 只创建一条8D记录 |  |
```

**动手练习（用8D工作台）**
1. 给8D工作台 T04「客诉创建」功能写5个正向测试用例 + 5个边界测试用例
2. 同样给 T05「D3→D4门禁状态流转」写测试用例，覆盖：
   - 品质主管审批通过 → 状态变为D4 ✅
   - 普通操作工点审批 → 拒绝 ❌
   - 品质主管审自己当组长的8D → 拒绝（自审冲突）❌
   - 状态不是D3时点审批 → 拒绝 ❌

**考核标准**
- 能对单功能写出10个以上测试用例
- 覆盖正向、边界、异常三种场景
- 测试用例格式规范，预期结果明确可验证

📝 **课前自测**：5道选择题（正向测试/边界测试/异常测试的概念区分）
📋 **课后对比**：你给「客诉创建」写的测试用例 vs AI写的测试用例 → 对比覆盖度差异**

### 第7课：Bug定位 — 用Console「听诊」

> **核心理念**：设备坏了，老师傅听声音就知道哪的问题。系统出问题，你要学会用浏览器Console「听诊」。

**学习目标**
- 掌握浏览器Console（控制台）和Network面板的基础使用
- 能看懂常见报错信息的含义
- 能从报错判断问题属于前端、后端、还是网络

**报错速查表**

| 报错类型 | 含义 | 通常原因 |
|---------|------|---------|
| `Uncaught TypeError: xxx is not a function` | xxx不是一个函数 | 方法名拼错了，或对象还没创建 |
| `Cannot read property 'xxx' of null` | 读不到xxx属性 | API还没返回数据就去读 |
| `404 Not Found` | 找不到 | API地址写错了 |
| `500 Internal Server Error` | 服务器内部错误 | 后端代码报错 |
| `Network Error` / `ERR_CONNECTION_REFUSED` | 连不上 | 服务器没启动 |
| `401 Unauthorized` | 没权限 | JWT过期或没传token |

**动手练习**
1. 打开8D工作台前端，在开发者工具中切换到Network面板，刷新页面，观察API请求：请求的URL是什么？服务器返回了什么数据？状态码是多少？
2. 故意触发一个错误（如：调用一个不存在的API地址），看Console中的报错信息，判断错误类型
3. 给你3个报错场景，判断是前端bug、后端bug、还是配置/网络问题：
   - 场景A：点「保存」按钮，Console报 `POST /api/8d 500`
   - 场景B：页面白屏，Console报 `dd is not defined`
   - 场景C：点「登录」，Console报 `POST /api/auth/dingtalk 401`

**考核标准**
- 能打开Console并看懂报错信息
- 能从报错判断问题出在前端还是后端
- 能用Network面板追踪一次完整的请求-响应过程

📝 **课前自测**：5道选择题（报错类型匹配：500/404/401/Network Error分别什么意思）
📋 **课后对比**：给你3个报错场景，你先判断原因 → AI判断 → 对比你们哪里判断一致/不一致**

### 第8课：综合验收 — 判断AI交付能不能上线

> **核心理念**：AI交付了一个功能到你手里，你怎么判断它能上线还是不能上线？用这套验收流程，有理有据地做决策。

**学习目标**
- 建立完整的交付验收流程
- 能综合运用L1（审查）+ L2（验证）做全面判断
- 能输出明确的「可上线/有条件上线/不可上线」判断

**验收决策矩阵**

| 情况 | 判断 | 示例 |
|------|------|------|
| 功能全部实现 + 无bug + 边界正常 | ✅ 可上线 | 客诉CRUD全部API通过，表单验证完整 |

| 核心功能缺失 | ❌ 不可上线 | D3→D4门禁逻辑没实现 |

**动手练习**

   - 用第6课的方法执行功能测试
   - 用第7课的方法检查Console无报错
3. 输出验收报告，做出上线判断

**考核标准**
- 验收报告覆盖：功能完整性、UI符合性、逻辑正确性、边界处理
- 给出有理有据的上线判断
- 如果退回，退回原因是AI能直接理解并修改的具体描述

📝 **课前自测**：5道选择题（验收决策矩阵：可上线/有条件上线/不可上线的判断标准）
📋 **课后对比**：你的验收报告 vs AI的验收报告 → 上线判断一致还是冲突？根源在哪？

## Part 3：能沟通 — 让AI准确理解你的需求

### 第9课：Prompt工程 — 说AI能听懂的话

> **核心理念**：AI像一个超级聪明但没有任何行业常识的新员工。你跟他说「做个8D系统」，他一脸懵。你说清楚每一步要什么，他就能做对。

**学习目标**
- 理解Prompt四要素框架
- 能用精确指令得到精确结果
- 掌握对比实验方法：好Prompt vs 差Prompt

**有效Prompt四要素**

```
1. 上下文（Context）→ 项目背景、用什么技术、有什么约束
2. 任务（Task）     → 具体要做什么，不说「优化」，说「把xx从A改成B」
3. 约束（Constraints）→ 不能改什么、必须遵守什么、用什么格式
4. 输出格式（Format）→ 要代码块还是表格还是文字
```

**不良 vs 良好Prompt对比**

| ❌ 不良 | ✅ 良好 |
|--------|--------|
| 「帮我做个气泡图」 | 「在 bubble-chart-demo.html 中新增第5个案例卡片：'客户投诉趋势'。X轴=月份(1-12月)，Y轴=投诉次数，气泡大小=涉及金额，颜色按投诉类型区分（尺寸/表面/装配/材料）。参照现有4个案例的代码结构，保持一样的样式和布局。」 |
| 「修一下8D工作台的bug」 | 「8D工作台 D3→D4 门禁中，当品质主管也是该8D的组长时，应该拒绝并提示'不能审核自己负责的8D'。目前代码在 submit_g3() 函数中没有执行这个检查。请参照 T05 中的 G3自审冲突 逻辑修复。」 |

**动手练习**
1. 给气泡图项目提一个新需求（如：增加响应式适配，手机端4列变1列），分别用差Prompt和好Prompt发给AI，对比两次输出的质量，记录差异
2. 给8D工作台提一个需求（如：仪表盘加「本周新增8D数」统计卡片），用四要素写Prompt
3. 总结你的发现：哪些信息给了AI会显著提升输出质量？

**考核标准**
- 所有Prompt都包含四要素
- 对比实验中能看到好Prompt的明显优势
- 能总结出至少3条自己的Prompt经验

📝 **课前自测**：5道选择题（Prompt四要素的识别：哪条是上下文/任务/约束/格式）
📋 **课后对比**：你写的Prompt vs AI帮你改写的Prompt → 哪个输出质量更高？为什么？

### 第10课：需求拆解 — 把想法变成AI可执行的任务

> **核心理念**：「做个质量管理看板」——这句话AI接不住。但拆成5个小任务，每个带明确完成标准，AI就能一个一个做对。

**学习目标**
- 掌握用户故事拆解方法
- 能把一个业务需求拆成AI可独立完成的任务列表
- 为每个任务定义可验证的完成标准

**拆解方法**

```
用户故事：「作为品质主管，我想要一个质量缺陷气泡图看板，
          以便一眼识别最需要优先处理的缺陷类型」

拆解后：
├── 任务1：创建新案例卡片框架
│   └── 完成标准：HTML中新增第5个<div class="card">，空但渲染正常
├── 任务2：准备模拟数据并映射到SVG坐标
│   └── 完成标准：8个气泡显示在正确位置，X=频次 Y=严重度
│       需确认：频次0-50次映射到X轴60-500px的公式
├── 任务3：实现颜色映射（缺陷类型→颜色）
│   └── 完成标准：尺寸超差=红、表面缺陷=橙、装配不良=紫、材料问题=青
├── 任务4：添加洞察分析文本框
│   └── 完成标准：卡片底部显示洞察文字，格式参照现有4个案例
└── 任务5：在页面顶部添加导航跳转
```

**考核标准**

### 第11课：评审AI的技术方案

> **核心理念**：你不需要能设计技术架构。但你要能看懂AI设计的方案，并从业务角度判断它是否合理。

**学习目标**
- 理解前后端分离架构的基本概念
- 能从功能、风险、成本三个角度评审AI的技术方案
- 能用业务语言和AI讨论技术决策

**评审架构的三个角度**

```
1. 功能角度：这个方案能实现所有需求吗？有没有漏掉的？
2. 风险角度：最容易出问题的地方在哪？（数据丢失？权限漏洞？性能瓶颈？）
3. 成本角度：实现复杂度合理吗？有没有「杀鸡用牛刀」的过度设计？
```

**动手练习**
1. AI给8D工作台的知识库检索（T17）出了一个技术方案。方案说「用Elasticsearch做全文检索」
2. 你从三个角度评审：
   - 功能：确实能实现全文搜索 ✅
   - 风险：erpserver只有15GB内存，装ES可能撑不住 ⚠️
   - 成本：引入ES=多一套系统要维护，不如直接用PostgreSQL的 `ILIKE` + `tsvector` ❌
3. 向AI反馈，让它改用PostgreSQL方案重新设计
4. 记录：你提出了什么问题，AI的方案做了什么调整

**考核标准**
- 能从三个角度对AI方案各提出至少一个问题
- 问题聚焦业务影响和合理性，而非技术细节
- 能判断AI修改后的方案是否解决了你的顾虑

📝 **课前自测**：5道选择题（功能/风险/成本三个角度分别关注什么）
📋 **课后对比**：你评审AI方案的意见 vs AI自评 → 你发现的风险点，AI自己意识到了吗？

### 第12课：建立你的AI开发工作流

> **核心理念**：12课学完，你要的不是一堆散装技能，而是一套可复制的流程。以后任何AI开发项目，你都能用这套流程管起来。

**学习目标**
- 建立从需求到上线的完整AI协作工作流
- 定义每个环节你需要做什么、AI交付什么
- 建立质量门禁标准

**AI协作工作流**

```
第1步：需求定义（你主导）
├── 写出用户故事 → 拆解为独立任务 → 定义完成标准
└── 输出：需求规格

第2步：方案评审（你和AI协作）
├── AI给出技术方案 → 你从功能/风险/成本评审 → 迭代到一致
└── 输出：技术方案确认

第3步：分批交付（AI主导，你监督）
├── AI按任务逐个开发 → 每个任务完成后你验收
├── 通过→下一个 / 不通过→退回附审查记录
└── 输出：逐批交付的功能模块

第4步：集成验收（你主导）
├── 全部任务完成后联调 → 回归测试 → 上线判断
└── 输出：上线审批
```

**质量门禁（每个环节的Go/No-Go）**

| 环节 | 通过标准 | 不通过动作 |
|------|---------|-----------|
| 需求评审 | 任务拆解合适，完成标准可测试 | 重新拆解 |
| 方案评审 | 三个角度的问题都得到满意回答 | 重新设计 |
| 单功能验收 | 功能正常 + 无报错 + 边界处理完善 | 退回修改（附审查记录） |
| 集成验收 | 全部功能正常 + 已有功能不受影响 | 修复后重测 |

**结业考核**
1. 从气泡图或8D工作台中选一个新功能
2. 独立走完整工作流：需求→方案→分批交付→集成验收
3. 提交你的全流程审查报告 + AI独立审查报告 → 对比式反馈作为参考
4. **Jacky人工评审**：你建立的判断力是否已能独立管好一个AI开发项目？

📝 **课前自测**：5道选择题（AI协作工作流四步+质量门禁的Go/No-Go标准）
📋 **课后对比**：无（本课为结业考核，由Jacky人工评审）

## 四、考核机制

> **核心原则**：有标准答案的（选择题、概念判断）用自动评分。没有标准答案的（代码审查、方案评审）用**对比式反馈**——你的判断 vs AI的判断，找出差异，分析原因，从差异中学习。

### 4.1 两类考核方式

| 类型 | 题目形式 | 评分方式 | 适用 |
|------|---------|---------|------|
| **客观题** | 选择题、判断题、概念匹配 | 自动评分（有标准答案） | 课前测、概念题 |
| **对比式反馈** | 代码审查意见、Bug描述、验收报告、方案评审 | 你的判断 vs AI的判断，标记差异，分析谁更有道理 | 课后练、实操任务、阶段考 |

### 4.2 对比式反馈机制

> **为什么不用 AI 自动评分？** 用来改卷的 AI 自己也有偏见。一段代码可能「功能正确但性能差」「逻辑错误但不影响运行」「边界没处理」。AI 说你对不代表你真对，AI 说你错也不代表你真错。你需要的不是「AI 说你几分」——而是「你和 AI 看到的不一样时，谁的更有道理」。

**对比式反馈输出格式：**

```
━━━━━━━━━━━━━━━━━━━━━━
📋 实操任务：审查8D工作台 T05 D3门禁逻辑

【你的审查意见】
  ✓ 发现1：第47行，只检查了 role === "quality_manager"，没检查自审冲突
  ✓ 发现2：第52行，错误提示语不明确——用户不知道被拒绝的具体原因
  ✗ 你提到："密码字段没有加密" → 实际上 JWT token 已处理认证，前端不存在密码字段

【AI 的审查意见】
  ✓ 发现1：第47行，缺少自审冲突检查 ← 你已发现 ✅
  ✓ 发现2：第52行，拒绝提示不明确 ← 你已发现 ✅
  ✓ 发现3：第62行，状态非D3时未拦截，会导致用户在错误阶段提交
  ✓ 发现4：第38行，fetch 没有 .catch() 处理网络异常

【差异对比】
┌────────────────┬──────────┬──────────┬────────────┐
│ 发现的内容       │ 你发现了  │ AI发现了  │ 差异分析     │
├────────────────┼──────────┼──────────┼────────────┤
│ 自审冲突检查     │    ✅    │    ✅    │ 一致        │
│ 错误提示不明确   │    ✅    │    ✅    │ 一致        │
│ 状态门禁缺失     │    ❌    │    ✅    │ 👈 你没发现  │
│ 网络异常未处理   │    ❌    │    ✅    │ 👈 你没发现  │
│ 「密码未加密」   │    ✅    │    ❌    │ 👈 你误报了  │
└────────────────┴──────────┴──────────┴────────────┘

【学习要点】
  → 你漏掉的第1个：状态门禁——这是逻辑层面的判断，不仅要看明文逻辑，还要看隐式前置条件
  → 你漏掉的第2个：异常处理——AI的代码常常只写正常路径，异常分支是审查重点
  → 你误报的：在审查前先确认系统架构——8D工作台用JWT做认证，前端没有密码概念
```

**这个机制培养的能力恰好是你需要的：**

| 传统评分 | 对比式反馈 |
|---------|-----------|
| AI说你对→ 你学会取悦AI | 你和AI不一致→ 你学会判断「谁更有道理」 |
| 追求「满分」 | 追求「缩小与AI的差异」 |
| 结果为王 | 过程为学习材料 |
| 一次判对错 | 持续迭代判断力 |

### 4.3 每课时考核流

```
课前测（选择题/自动评分）→ 课时学习 → 课后练（对比式反馈）
                                              ↓
阶段考：客观题(自动评分) + 实操(对比式反馈) → 阶段报告
                                              ↓
                          毕业项目答辩（Jacky人工评审）
```

### 4.4 计分规则

| 考核项 | 形式 | 评分方式 | 用途 |
|--------|------|---------|------|
| 课前自测 | 5道选择题 | 自动评分 | 测现有认知，不计通过 |
| 课后练习 | 3道对比式反馈 | AI对比差异，不评分 | 理解你漏了什么、误报了什么 |
| 阶段考核 | 客观题(10分) + 实操对比(10分) | 客观题自动 + 实操看差异覆盖度 | 追踪能力成长 |
| 毕业答辩 | 全流程项目 | Jacky人工评审 | 最终判断 |

> **实操不计「分数」，计「差异覆盖度」**：AI发现的N个问题中你发现了几个？你发现的M个中AI确认了几个？这个比例随课程进行应逐步提升。

### 4.5 实操任务：真实场景对齐

> 实操任务是整个培训中价值密度最高的环节。用抽象的"订单处理函数"做练习，学员学完也不知道怎么用到自己工作中。

**任务来源：直接从8D工作台和气泡图的真实功能中选取。**

| 阶段 | 实操任务 | 任务来源 | 练什么 |
|------|---------|---------|--------|
| 阶段一 | 打开气泡图项目，让AI解释YOLO检测/标注相关代码逻辑 | bubble-chart | L1-看懂代码 |
| 阶段二 | 给8D工作台一个现有功能写验收清单，逐项测试 | 8D工作台 | L2-功能测试 |
| 阶段三 | 产品工程师提出"加一个原因分析进度追踪面板"，写需求规格 | 8D工作台真实需求 | L2→L3-需求翻译 |
| 阶段四 | 独立完成一个功能：需求→AI生成→审查→验收→上线 | 8D工作台或气泡图新功能 | L3-全流程 |

**实操任务三要素**（每课必须声明）：

| 要素 | 说明 | 示例 |
|------|------|------|
| 任务场景 | 在哪个真实系统中完成 | "在8D工作台的问题详情页中" |
| 验收标准 | 怎么算完成 | "能列出至少3处AI代码的逻辑漏洞，并说出为什么是漏洞" |
| 参考输出 | 完成后提交什么 | "提交一段文字：你发现了什么问题，AI的解释是什么，你的判断是什么" |

### 4.6 毕业条件

- [ ] 12课时全部完成
- [ ] 4个阶段考客观题均≥60分
- [ ] 毕业项目答辩通过（Jacky人工评审）
- [ ] 累计学习时长≥8小时

### 4.7 评审机制

| 评审节点 | 评审人 | 评审内容 | 评分方式 |
|----------|--------|---------|---------|
| 课前测 | 系统自动 | 5道选择题 | 自动评分 |
| 课后练 | 对比式反馈 | 你的审查意见 vs AI的审查意见 | 标记差异，不评分 |
| 阶段考客观题 | 系统自动 | 概念选择题+填空题 | 自动评分 |
| 阶段考实操 | 对比式反馈 | 代码审查/验收报告/方案评审 | 差异覆盖度分析 |

| 毕业答辩 | Jacky | 全流程项目：需求→审查→验收 | 人工评审 |

### 4.8 错误库：把踩过的坑变成培训弹药

> 你和AI合作中踩过的每一个坑，都是培训中最珍贵的教材。这些真实案例比任何理论讲解都有说服力。

**错误库是独立模块，持续积累、永不删除：**

```
content/
└── errors/
    ├── index.json          ← 错误分类索引
    ├── E001.json           ← 单个错误案例
    ├── E002.json
    └── ...
```

**单个错误案例的JSON结构：**

```json

    "project": "气泡图",
    "person": "Jacky",
    "date": "2026-07-14"
```

**错误库的使用方式：**
